# Бронирование переговорной

Интерфейс бронирования переговорной комнаты на рабочий день (09:00–18:00).

**Стек:** React 18 + TypeScript (strict) + Vite, TanStack Query (серверное состояние), React Hook Form + zod (формы и контракт API), MSW (mock API), Vitest + Testing Library, ESLint + Prettier. Структура — [Feature-Sliced Design](https://feature-sliced.design/). Стили — обычный CSS без UI-библиотек.

- Демо: https://maddev-test.vercel.app/
- Репозиторий: https://github.com/ponkk513/maddev-test

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # 52 теста: бизнес-правила, mock API, UI-сценарии
npm run lint       # ESLint, включая правила слоёв FSD
npm run format     # Prettier
npm run check      # всё сразу: типы + линтер + формат + тесты
npm run build      # проверка типов + production-сборка в dist/
npm run preview    # посмотреть production-сборку
```

Нужен Node.js 18+. Mock API работает и в production-сборке (через Service Worker), поэтому демо на Vercel/Netlify — это обычный статический хостинг без бэкенда.

## Что сделано

### Функциональность

- Выбор даты: стрелки «предыдущий/следующий день», нативный date picker, кнопка «Сегодня». Дата хранится в URL (`?date=2030-03-05`), работают «назад/вперёд» в браузере.
- Таймлайн дня с сеткой по 30 минут: занятые, свободные и прошедшие слоты, линия «сейчас». Клик по свободному слоту подставляет время в форму (по умолчанию 1 час, с укорачиванием до следующей брони). Клик по брони открывает её на редактирование.
- Превью выбранного интервала прямо на таймлайне (красное, если интервал невалиден).
- Список броней на день с действиями «Изменить» / «Удалить» (удаление — через диалог подтверждения).
- Форма создания/редактирования: начало и окончание с шагом 15 минут, необязательное название. Форма заранее заполнена первым свободным интервалом.

### Бизнес-правила

Все правила — чистые функции в [`entities/booking/model/rules.ts`](src/entities/booking/model/rules.ts) (время «сейчас» передаётся параметром). Один и тот же код используется в форме (через zod-схему для React Hook Form) для мгновенной обратной связи и в mock-сервере как источник истины.

| Правило                                    | Реализация                                                                                                                                                       |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| В пределах 09:00–18:00                     | `OUTSIDE_WORKING_HOURS`; в селектах нет вариантов вне дня                                                                                                        |
| start < end                                | `START_NOT_BEFORE_END`                                                                                                                                           |
| 30 мин ≤ длительность ≤ 2 ч                | `TOO_SHORT` / `TOO_LONG`                                                                                                                                         |
| Без пересечений, касание границ допустимо  | полуинтервалы `[start, end)`: `a.start < b.end && b.start < a.end`                                                                                               |
| Нельзя бронировать прошлое                 | прошедшие даты — форма недоступна; сегодня — прошедшее время отключено в селектах и отклоняется валидацией (`PAST_TIME`). Время «сейчас» обновляется каждые 30 с |
| Редактирование не конфликтует само с собой | `findConflicts(draft, bookings, excludeId)`                                                                                                                      |
| Сервер может вернуть 409                   | см. ниже                                                                                                                                                         |

### Конфликт 409

Сервер проверяет правила заново и не доверяет клиенту. При ответе 409:

1. над кнопкой появляется понятное сообщение с указанием, _какая_ бронь мешает (`role="alert"`, на него переводится фокус);
2. список броней на дату перезапрашивается (инвалидация запроса после любой мутации — успешной или нет);
3. введённые данные не теряются: пока форма «нетронута», её значения следуют за внешними данными (первый свободный слот или редактируемая бронь — проп `values` у React Hook Form); после первого изменения — или в момент отправки — значения принадлежат пользователю, и фоновое обновление списка их не перезаписывает ([`useBookingForm.ts`](src/features/booking-form/model/useBookingForm.ts));
4. после обновления списка поля перепроверяются, и рядом с ними появляется новая причина конфликта.

Похожим образом обработаны: 404 при редактировании (бронь удалили — форма переходит в режим создания с теми же данными), 404 при удалении (цель достигнута, просто обновляем список), 5xx и сетевые ошибки (сообщение, данные формы сохраняются).

**Как воспроизвести 409:** раскройте «Инструменты демо» внизу страницы и включите «кто-то успевает занять это время», либо откройте приложение в двух вкладках — данные mock-сервера лежат в `localStorage` и общие для вкладок, — создайте бронь в одной вкладке и попробуйте занять то же время во второй.

**Как посмотреть ошибки сервера:** в тех же инструментах включите «Сервер недоступен» — все запросы будут отвечать 500 (переключите дату, чтобы увидеть экран ошибки загрузки, или попробуйте сохранить бронь). Там же — задержка сети для просмотра состояний загрузки и отправки.

### Состояния UI

- загрузка — скелетон таймлайна, `aria-busy`; форма заблокирована, пока брони не загружены (иначе подсказка свободного времени считалась бы по пустому списку); фоновое обновление — ненавязчивая метка «Обновление…» без потери данных на экране;
- пустое состояние — «Броней нет — комната свободна весь день»;
- ошибка загрузки — сообщение и кнопка «Повторить»; если упало фоновое обновление, старые данные остаются на экране;
- отправка формы — кнопка «Сохранение…», защита от повторной отправки;
- результат действия — уведомление в live-регионе (`role="status"`).

### Архитектура

Код разложен по слоям [Feature-Sliced Design](https://feature-sliced.design/). Слой может импортировать только нижележащие слои, а другие слайсы — только через их public API (`index.ts`). Оба правила проверяет ESLint (`no-restricted-imports`, см. [`eslint.config.js`](eslint.config.js)).

```
src/
  app/                    точка входа, провайдеры (QueryClient, уведомления), глобальные стили
  pages/booking/          страница — только компоновка виджетов и фич
  widgets/
    day-schedule/         таймлайн дня + состояния загрузки/ошибки
    day-bookings/         список броней + удаление + фокус после удаления
  features/
    booking-form/         создание/редактирование: React Hook Form + zod, обработка 409/404/5xx
    delete-booking/       подтверждение и удаление, обработка 404
    select-date/          выбор даты, синхронизация с ?date=
  entities/booking/
    model/                типы, бизнес-правила, слоты, zod-схемы контракта (+ тесты)
    api/                  BookingsApi, хуки TanStack Query, разбор ошибок домена (409/422)
    ui/                   BookingList (действия передаются слотом из фич)
    lib/                  форматирование
  shared/
    api/                  fetch-клиент: JSON, валидация ответа zod-схемой, ApiError
    lib/                  время (HH:mm ⇄ минуты, даты), useNow
    ui/                   ConfirmDialog (<dialog>), ErrorState, уведомления (live-регион)
    config/               переменные окружения
  mocks/                  mock-сервер (MSW): хранилище, обработчики, dev-панель — вне слоёв
  test/                   настройка тестов, тестовый сервер
```

**Валидация в трёх местах, с одним источником правил:**

- `entities/booking/model/rules.ts` — бизнес-правила как чистые функции;
- `entities/booking/model/schema.ts` — zod-схемы _формы данных_ контракта. Сервер разбирает ими тело запроса (некорректная форма → 400), клиент — ответы API (неожиданный ответ → понятная ошибка, а не падение в рендере);
- `features/booking-form/model/schema.ts` — схема формы для React Hook Form: тонкий адаптер, который превращает правила и пересечения в ошибки полей.

UI зависит только от интерфейса `BookingsApi`. Чтобы подключить реальный бэкенд с тем же контрактом:

```bash
VITE_USE_MOCKS=false VITE_API_URL=https://api.example.com npm run build
```

MSW при этом не попадает в бандл (подключается динамическим импортом).

**Контракт API**

| Метод                               | Ответы                                    |
| ----------------------------------- | ----------------------------------------- |
| `GET /api/bookings?date=YYYY-MM-DD` | `200 Booking[]`, `400`                    |
| `POST /api/bookings`                | `201 Booking`, `400`, `409`, `422`        |
| `PATCH /api/bookings/:id`           | `200 Booking`, `400`, `404`, `409`, `422` |
| `DELETE /api/bookings/:id`          | `204`, `404`, `422`                       |

`400` — тело запроса не соответствует контракту, `422` — нарушено бизнес-правило. Тело ошибки: `{ code, message, ...details }`, где `code` — `CONFLICT` (+ `conflicts: Booking[]`), `VALIDATION` (+ `issues`), `BOOKING_LOCKED`, `NOT_FOUND`, `BAD_REQUEST`, `INTERNAL`.

### Адаптивность и доступность

- Одна колонка на мобильных (форма сверху), две колонки от 880px.
- Семантическая разметка: заголовки, `label` у всех полей, списки, `<dialog>` для подтверждения (ловушка фокуса и Esc).
- Ошибки привязаны к полям через `aria-invalid` / `aria-describedby`; при неудачной отправке фокус уходит на первое невалидное поле (`shouldFocusError` в RHF) или на сообщение сервера. После удаления брони фокус возвращается к заголовку списка.
- `eslint-plugin-jsx-a11y` в режиме recommended.
- Всё доступно с клавиатуры, видимый `:focus-visible`. Цвет — не единственный индикатор (у слотов есть текст и штриховка).
- Блоки броней на таймлайне скрыты от скринридеров (`aria-hidden`), потому что дублируют доступный список с кнопками.

### Тесты

- `entities/booking/model/*.test.ts` — правила: границы дня, длительности, касание границ, прошлое время, редактирование без самоконфликта.
- `mocks/handlers.test.ts` — mock API через настоящий HTTP-клиент: 201/400/404/409/422/500, некорректное тело запроса, гонка за слот.
- `pages/booking/ui/BookingPage.test.tsx` — UI: загрузка, пустое состояние, ошибка загрузки с повтором, 500 при сохранении, создание, валидация, **409 с сохранением ввода и обновлением списка** (в том числе когда пользователь отправил предложенное время, не трогая форму), редактирование, удаление, прошедшая дата.

## Решения и допущения

- **Начавшуюся бронь нельзя изменить или удалить** — менять прошлое бессмысленно; правило проверяет и UI, и сервер (`BOOKING_LOCKED`).
- **Дату брони при редактировании менять нельзя** — только время и название. Перенос на другой день = удалить + создать. Это упрощает проверку конфликтов (нужны брони только одной даты).
- Для сегодняшнего дня доступно время, начиная с ближайших 15 минут после текущего момента.
- Время интерпретируется в локальном часовом поясе браузера. Для реального сервера часовой пояс комнаты нужно передавать явно (см. «Что не сделано»).
- MSW выбран вместо Route Handlers, потому что in-memory store в serverless-функциях не переживает холодный старт и не общий между инстансами — демо вело бы себя непредсказуемо.

## Что не сделано

- Часовые пояса: клиент и сервер считаются в одном поясе.
- Оптимистичные обновления — сознательно нет: при частых конфликтах они дают «мигание» данных; задержка mock API небольшая.
- Перенос брони на другую дату, повторяющиеся брони, несколько комнат, авторизация/«мои брони».
- E2E-тесты в реальном браузере (Playwright) и автоматическая проверка a11y (axe).
- Из правил FSD не проверяется запрет кросс-импортов между слайсами _одного_ слоя (сейчас их нет; для автоматической проверки подойдёт [Steiger](https://github.com/feature-sliced/steiger)).
- Стили — один глобальный файл с BEM-подобными классами, без CSS Modules.
